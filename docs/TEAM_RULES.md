# PickPlace 팀 개발 규칙

이 문서는 PickPlace 프로젝트의 협업 품질을 유지하고 Git 충돌과 작업 누락을 줄이기 위한 공통 규칙이다. 모든 팀원은 작업을 시작하기 전에 이 문서를 확인하며, 규칙 변경은 팀 합의와 Pull Request를 통해 진행한다.

## 1. 기본 원칙

1. `main`과 `develop` 브랜치에는 직접 커밋하거나 푸시하지 않는다.
2. 모든 작업은 이슈 생성, 작업 브랜치 생성, 코드 작성, Pull Request, 리뷰, 병합 순서로 진행한다.
3. 한 브랜치와 한 Pull Request에는 하나의 목적만 담는다.
4. 동작하지 않는 코드, 테스트하지 않은 코드, 비밀정보가 포함된 코드는 공유 브랜치에 병합하지 않는다.
5. 다른 팀원의 코드를 임의로 대규모 수정하지 않는다. 필요한 경우 먼저 담당자와 범위를 협의한다.
6. 작업 중 발견한 별도 문제는 현재 작업에 섞지 않고 새로운 이슈로 등록한다.
7. 일정이나 구현 방향에 영향을 주는 문제는 혼자 오래 붙잡지 않고 팀에 공유한다.

## 2. 역할과 책임

| 담당        | 주요 책임                                                      |
| ----------- | -------------------------------------------------------------- |
| 팀장·풀스택 | 일정 및 범위 관리, 프론트엔드·백엔드 연동, 릴리스 관리         |
| 백엔드      | API, 데이터베이스, 인증, 데이터 수집·가공 로직 개발            |
| 인공지능    | 데이터 전처리, 모델 학습·평가, 추론 API 및 결과 설명 기준 개발 |

- 역할은 주요 책임을 나타낼 뿐이며 특정 영역의 코드 소유권을 독점하지 않는다.
- 다른 영역을 수정할 때에는 해당 담당자를 리뷰어로 지정한다.
- API, 데이터 스키마, 모델 입출력 형식처럼 여러 영역에 영향을 주는 변경은 구현 전에 팀과 합의한다.

## 3. Git Flow 브랜치 전략

### 3.1 장기 브랜치

| 브랜치    | 용도                       | 규칙                      |
| --------- | -------------------------- | ------------------------- |
| `main`    | 발표·배포 가능한 안정 버전 | 릴리스와 긴급 수정만 병합 |
| `develop` | 다음 버전을 위한 통합 개발 | 기능·수정 PR의 기본 대상  |

### 3.2 작업 브랜치

| 유형         | 생성 기준                | 병합 대상              | 예시                          |
| ------------ | ------------------------ | ---------------------- | ----------------------------- |
| `feature/*`  | 새로운 기능              | `develop`              | `feature/42-commercial-score` |
| `fix/*`      | 일반 버그 수정           | `develop`              | `fix/57-empty-chart`          |
| `refactor/*` | 동작 변경 없는 구조 개선 | `develop`              | `refactor/31-data-loader`     |
| `docs/*`     | 문서 변경                | `develop`              | `docs/18-api-guide`           |
| `test/*`     | 테스트 추가·개선         | `develop`              | `test/24-score-service`       |
| `chore/*`    | 설정, 의존성, 빌드 작업  | `develop`              | `chore/12-ci-setup`           |
| `release/*`  | 배포 준비                | `main`, 이후 `develop` | `release/0.1.0`               |
| `hotfix/*`   | 배포본의 긴급 오류 수정  | `main`, 이후 `develop` | `hotfix/0.1.1`                |

### 3.3 브랜치 이름 규칙

- 영문 소문자와 숫자, 하이픈을 사용한다.
- 가능하면 이슈 번호를 포함한다.
- 이름만 보고 작업 목적을 이해할 수 있게 작성한다.
- 개인 이름만 사용한 브랜치는 만들지 않는다.

```text
feature/42-commercial-score
fix/57-empty-analysis-result
docs/18-development-guide
```

### 3.4 저장소 최초 설정

현재 저장소처럼 기본 브랜치가 `master`라면 팀장 또는 저장소 관리자가 팀원과 적용 시점을 합의한 뒤 한 번만 `main`으로 변경한다.

```bash
git switch master
git branch -m main
git push -u origin main
```

원격 저장소에서 기본 브랜치를 `main`으로 변경한 후 `develop`을 생성한다.

```bash
git switch -c develop
git push -u origin develop
```

설정이 끝나면 원격 저장소에서 `main`과 `develop`을 보호 브랜치로 지정하고 직접 푸시와 강제 푸시를 제한한다. 기존 `master` 원격 브랜치 삭제는 모든 팀원이 새 브랜치 구성을 확인한 뒤 저장소 관리자가 수행한다.

## 4. 작업 시작 및 Git Pull 규칙

### 4.1 새로운 작업을 시작할 때

먼저 작업 트리가 깨끗한지 확인한다.

```bash
git status
```

커밋하지 않은 변경이 있다면 작업 목적에 맞게 커밋한다. 임시 변경을 무조건 `stash`로 숨기지 말고, 왜 남아 있는 변경인지 먼저 확인한다.

그다음 원격 저장소의 최신 정보를 가져오고 `develop`을 최신 상태로 만든다.

```bash
git switch develop
git fetch origin --prune
git pull --rebase origin develop
```

최신 `develop`에서 작업 브랜치를 생성한다.

```bash
git switch -c feature/42-commercial-score
```

### 4.2 작업 브랜치를 최신 상태로 맞출 때

개인이 단독으로 사용하는 작업 브랜치는 `develop`을 기준으로 리베이스한다.

```bash
git fetch origin --prune
git rebase origin/develop
```

충돌을 해결한 후 다음 명령을 실행한다.

```bash
git add <해결한-파일>
git rebase --continue
```

리베이스를 취소해야 하면 다음 명령을 사용한다.

```bash
git rebase --abort
```

### 4.3 Pull 관련 금지사항

- 변경사항이 남아 있는 상태에서 무작정 `git pull`을 실행하지 않는다.
- 원인을 이해하지 못한 충돌을 임의로 해결하지 않는다.
- `main`과 `develop`에는 강제 푸시하지 않는다.
- 다른 팀원이 함께 사용하는 브랜치는 합의 없이 리베이스하지 않는다.
- 개인 작업 브랜치를 리베이스한 경우에만 `--force-with-lease` 사용을 허용한다.
- `--force`는 사용하지 않는다.

```bash
git push --force-with-lease origin feature/42-commercial-score
```

공동 작업 브랜치라면 리베이스 대신 `develop`을 병합하거나 팀원과 먼저 방식을 합의한다.

## 5. 커밋 규칙

### 5.1 커밋 메시지

Conventional Commits 형식을 사용한다.

```text
<type>(<scope>): <summary>
```

| 타입       | 용도                                 |
| ---------- | ------------------------------------ |
| `feat`     | 새로운 기능                          |
| `fix`      | 버그 수정                            |
| `refactor` | 동작 변경 없는 구조 개선             |
| `docs`     | 문서 변경                            |
| `test`     | 테스트 추가·수정                     |
| `style`    | 포매팅 등 코드 의미에 영향 없는 변경 |
| `chore`    | 설정, 의존성, 빌드 및 기타 작업      |
| `perf`     | 성능 개선                            |
| `ci`       | CI/CD 설정 변경                      |

예시는 다음과 같다.

```text
feat(analysis): 상권 성장성 점수 계산 기능 추가
fix(api): 데이터가 없을 때 500 오류가 발생하는 문제 수정
refactor(model): 전처리 파이프라인 모듈 분리
docs(readme): 로컬 실행 방법 추가
```

### 5.2 커밋 작성 원칙

- 하나의 커밋에는 하나의 논리적 변경만 포함한다.
- 제목은 변경한 내용이 명확하게 드러나도록 작성한다.
- 의미 없는 메시지인 `수정`, `작업`, `update`, `test`는 사용하지 않는다.
- 커밋 전 변경 파일과 diff를 확인한다.
- 생성 파일, 개인 설정, 로그, 대용량 학습 데이터는 필요한 경우가 아니면 커밋하지 않는다.

```bash
git status
git diff
git diff --staged
```

## 6. Pull Request 규칙

### 6.1 PR 생성 전 확인

- 브랜치가 최신 `develop`을 반영하고 있는지 확인한다.
- 애플리케이션이 정상적으로 실행되는지 확인한다.
- 관련 테스트, 린트 및 포매터를 실행한다.
- 디버그 코드와 불필요한 로그를 제거한다.
- 비밀정보와 개인정보가 포함되지 않았는지 확인한다.
- API 또는 데이터 스키마 변경 시 관련 문서를 수정한다.

### 6.2 PR 제목

커밋 메시지와 같은 형식을 사용한다.

```text
feat(analysis): 상권 성장 가능성 분석 기능 추가
```

### 6.3 PR 본문 필수 항목

```markdown
## 작업 내용

- 구현하거나 수정한 내용을 작성

## 변경 이유

- 변경이 필요한 이유와 관련 이슈를 작성

## 확인 방법

1. 실행 방법
2. 테스트할 화면 또는 API
3. 예상 결과

## 영향 범위

- 프론트엔드, API, DB, AI 모델 등 영향받는 영역

## 체크리스트

- [ ] 로컬 실행 확인
- [ ] 테스트 통과
- [ ] 린트·포매팅 확인
- [ ] 문서 갱신
- [ ] 비밀정보 미포함

Closes #42
```

### 6.4 리뷰와 병합

- 최소 1명의 승인 후 병합한다.
- 공통 API, DB 스키마 또는 AI 입출력 변경은 관련 담당자의 승인을 받는다.
- 리뷰 요청 후에는 큰 변경을 별도 설명 없이 추가하지 않는다.
- 수정 요청은 반영 후 해당 대화에 결과를 남긴다.
- 작성자는 원칙적으로 자신의 PR을 단독 승인하지 않는다.
- 기능·수정 브랜치는 `develop`에 **Squash and merge**한다.
- 릴리스·핫픽스 브랜치는 이력을 보존하기 위해 merge commit으로 병합한다.
- 병합이 끝난 작업 브랜치는 원격과 로컬에서 정리한다.

## 7. 릴리스 및 핫픽스 절차

### 7.1 정식 릴리스

1. `develop`에서 `release/x.y.z` 브랜치를 생성한다.
2. 릴리스 브랜치에서는 버그 수정, 문서, 버전 정보만 변경한다.
3. 테스트가 끝나면 `main`으로 PR을 생성한다.
4. `main` 병합 후 동일 내용을 `develop`에도 반영한다.
5. `main`에 버전 태그를 생성한다.

```bash
git tag -a v0.1.0 -m "PickPlace v0.1.0"
git push origin v0.1.0
```

### 7.2 긴급 수정

1. `main`에서 `hotfix/x.y.z` 브랜치를 생성한다.
2. 긴급 오류에 필요한 최소한의 변경만 수행한다.
3. 검증 후 `main`과 `develop` 양쪽에 병합한다.
4. 수정 버전 태그를 생성한다.

## 8. 코드 작성 규칙

### 8.1 공통 규칙

- 프로젝트에 설정된 포매터와 린터 결과를 따른다.
- 변수와 함수 이름은 역할이 드러나도록 작성한다.
- 함수와 컴포넌트는 하나의 책임만 갖도록 작게 유지한다.
- 중복 로직은 공통 모듈로 분리하되, 한 번 사용되는 코드를 성급하게 추상화하지 않는다.
- 매직 넘버와 문자열은 의미 있는 상수로 정의한다.
- 주석은 코드가 무엇을 하는지보다 왜 그렇게 작성했는지를 설명한다.
- 사용하지 않는 코드, 주석 처리된 코드, 임시 디버그 출력은 제거한다.
- 오류를 숨기지 말고 사용자 또는 호출자가 처리할 수 있는 형태로 반환한다.
- 로그에는 비밀번호, 토큰, 개인정보 및 민감한 사업정보를 기록하지 않는다.
- 기존 프로젝트 구조와 명명 규칙이 있다면 이를 우선한다.

### 8.2 API 규칙

- 요청·응답 형식을 문서화한다.
- HTTP 상태 코드를 의미에 맞게 사용한다.
- 성공 응답과 오류 응답의 기본 구조를 일관되게 유지한다.
- 입력값은 서버에서 다시 검증한다.
- API 변경이 프론트엔드나 AI 서비스에 영향을 주면 PR에 명시한다.
- 호환성을 깨는 변경은 팀 합의 없이 진행하지 않는다.

### 8.3 데이터베이스 규칙

- 스키마 변경은 마이그레이션 파일로 관리한다.
- 이미 공유된 마이그레이션 파일을 임의로 수정하지 않고 새 마이그레이션을 추가한다.
- 테이블과 컬럼 이름은 프로젝트의 기존 규칙을 따른다.
- 대량 수정이나 삭제 쿼리는 영향 범위를 검증한 후 실행한다.
- 운영 또는 공유 데이터베이스에서 직접 실험하지 않는다.

### 8.4 AI 및 데이터 규칙

- 원본 데이터와 전처리 결과를 구분한다.
- 데이터 출처, 수집일, 기준 시점, 라이선스를 기록한다.
- 학습·검증·테스트 데이터 분리 기준을 문서화한다.
- 모델 성능은 사용한 데이터와 평가 지표를 함께 기록한다.
- 모델 파일과 대용량 데이터는 Git에 직접 올리지 않고 별도 저장소 또는 다운로드 절차를 사용한다.
- 난수 시드, 주요 하이퍼파라미터 및 실행 환경을 기록하여 결과를 재현할 수 있게 한다.
- 상권 진단 결과에는 점수뿐 아니라 주요 영향 요인과 신뢰도를 함께 제공한다.

## 9. 테스트 및 품질 기준

- 새로운 기능에는 정상 흐름과 주요 예외 상황을 확인하는 테스트를 작성한다.
- 버그 수정에는 가능하면 해당 문제가 다시 발생하지 않도록 회귀 테스트를 추가한다.
- 외부 API나 데이터가 없을 때의 동작도 확인한다.
- 테스트를 통과시키기 위해 실제 오류를 숨기거나 검증을 삭제하지 않는다.
- 테스트가 불가능한 부분은 PR에 이유와 수동 확인 방법을 작성한다.
- 발표 또는 릴리스 전에는 핵심 사용자 흐름을 팀이 함께 점검한다.

## 10. 환경변수와 보안

- API 키, 비밀번호, 인증서, 개인 계정정보는 Git에 커밋하지 않는다.
- 비밀정보는 `.env`에 저장하고 `.gitignore`에 포함한다.
- 필요한 환경변수 이름과 예시는 `.env.example`에 작성하되 실제 값은 넣지 않는다.
- 비밀정보가 커밋되었다면 파일 삭제만으로 끝내지 말고 즉시 키를 폐기하고 재발급한다.
- 실데이터에 개인정보가 포함되면 익명화하거나 지역 단위로 집계한다.
- 팀원의 개인 연락처나 학번 등 프로젝트 실행에 필요하지 않은 정보는 저장소에 올리지 않는다.

## 11. 이슈 및 작업 관리

모든 개발 작업은 이슈로 관리한다. 이슈에는 다음 내용을 포함한다.

- 작업 목적과 배경
- 구체적인 완료 조건
- 담당자
- 우선순위
- 관련 화면, API 또는 데이터
- 선행 작업과 의존성

작업 크기는 가능하면 1~3일 안에 리뷰 가능한 범위로 나눈다. 예상보다 작업이 커지면 기존 이슈의 범위를 임의로 넓히지 말고 하위 이슈로 분리한다.

## 12. 충돌 해결 규칙

1. 충돌이 발생하면 양쪽 변경의 의도를 먼저 확인한다.
2. 이해하기 어려운 코드의 충돌은 원 작성자와 함께 해결한다.
3. 충돌 표시를 삭제하는 것만으로 해결했다고 판단하지 않는다.
4. 해결 후 빌드, 테스트 및 주요 기능을 다시 확인한다.
5. DB 스키마, 잠금 파일, 설정 파일 충돌은 특히 주의한다.
6. 충돌 해결 과정에서 다른 팀원의 변경을 누락하지 않았는지 diff를 확인한다.

## 13. 팀 커뮤니케이션

- 작업을 시작할 때 이슈에 담당자와 진행 상태를 표시한다.
- API 또는 데이터 형식 변경은 구현 전에 관련 담당자에게 공유한다.
- 일정 지연이 예상되면 마감 직전이 아니라 확인 즉시 알린다.
- 중요한 결정은 구두 대화로 끝내지 않고 이슈, PR 또는 회의록에 남긴다.
- 리뷰 의견은 코드와 결과를 기준으로 작성하며 사람을 평가하는 표현을 사용하지 않는다.
- 의견이 다르면 목적, 근거, 대안과 영향 범위를 비교해 결정한다.

## 14. 완료 기준(Definition of Done)

다음 조건을 모두 만족해야 작업이 완료된 것으로 본다.

- 이슈의 완료 조건을 충족한다.
- 코드가 정상적으로 실행된다.
- 필요한 테스트를 통과한다.
- 린트와 포매팅 검사를 통과한다.
- 관련 문서와 `.env.example`이 갱신되었다.
- 민감정보와 불필요한 파일이 포함되지 않았다.
- 최소 1명의 리뷰 승인을 받았다.
- 대상 브랜치에 정상적으로 병합되었다.
- 병합 후 연결된 이슈와 작업 브랜치를 정리했다.

## 15. 일상 작업 흐름 요약

```text
1. 이슈 확인 또는 생성
2. develop 최신화
3. 작업 브랜치 생성
4. 작은 단위로 구현 및 커밋
5. 테스트·린트·포매팅 실행
6. develop 기준으로 최신화 및 충돌 해결
7. 원격 브랜치 푸시
8. Pull Request 생성
9. 리뷰 반영 및 승인
10. develop에 Squash and merge
11. 브랜치와 이슈 정리
```

이 문서에 없는 상황이 발생하면 임의로 처리하기보다 팀에 공유하고 합의한 내용을 문서에 추가한다.
