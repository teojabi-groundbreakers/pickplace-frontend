# 작업 및 문서화 규칙

## 적용 범위

2026-10-07 사용자 요청에 따라 앞으로 진행하는 모든 사안을 `docs/`에 정리합니다. 구현, 수정, 조사, 설계·기술 선택, 검토, 설정, 검증, 배포 및 미완료 사항이 대상입니다. 상세 내용은 이 폴더에 남기고, 장기적으로 참조할 핵심 문서는 루트 `AGENTS.md`에 연결합니다.

모든 Git 작업은 사용자가 제공한 [팀 개발 규칙](TEAM_RULES.md)을 따릅니다. 이 문서는 FE의 실행·문서화 방법을 보완하며, 팀 규칙의 Git Flow·이슈·커밋·PR·승인 절차를 대체하지 않습니다.

## 작업 절차

1. [문서 색인](README.md), [AGENTS.md](../AGENTS.md), [팀 개발 규칙](TEAM_RULES.md)과 관련 주제 문서를 읽어 기존 결정과 현재 제약을 확인합니다. Git 작업은 아래 Git Flow 절차를 따릅니다.
2. 작업 중 요청, 범위, 결정과 이유를 정리합니다. 조사 결과를 활용했다면 출처와 확인 날짜, 불확실한 내용을 함께 남깁니다.
3. 구현이나 설정을 바꾸면 기존 주제 문서를 갱신합니다. 새 주제는 목적이 드러나는 이름으로 문서를 만들고 색인에 추가합니다.
4. 중요한 참조가 새로 생기거나 변경되면 `AGENTS.md`의 링크·용도·주요 결정을 갱신합니다.
5. 영향 범위에 맞게 검증하고 실제 수행한 결과와 미수행·실패·보류 항목을 구분합니다.
6. [WORKLOG.md](WORKLOG.md)에 작업 기록을 추가하고, 최종 응답에서 필요한 문서를 안내합니다.

## 문서별 역할

- `TEAM_RULES.md`: 사용자 첨부 팀 개발 규칙 전문. Git Flow, 협업, 커밋·PR·리뷰, 코드·테스트·보안, 완료 기준의 원본입니다. 팀 합의와 PR 없이 규칙 내용을 임의로 바꾸지 않습니다.
- `FRONTEND.md`: 현재 구현과 사용·운영 방법. 과거 상태와 섞지 않습니다.
- `API.md`, `MAPS.md`: 주제별 사양, 설정, 제약과 결정 근거. 같은 설명을 여러 문서에 복제하기보다 원본 문서를 링크합니다.
- `WORKLOG.md`: 작업별 이력. 요청과 검증을 당시 시점으로 보존하며 후속 변경은 새 기록으로 남깁니다. 잘못된 사실은 수정 사실을 명시해 바로잡습니다.
- `README.md`: 문서 색인과 현재 기준. 새 문서와 현재 상태 변경을 반영합니다.
- 루트 `AGENTS.md`: 이후 작업자가 따라야 할 규칙과 주요 참조. 상세 사양의 원본은 `docs/`에 둡니다.

## 작업 기록 형식

Asia/Seoul 기준 날짜와 같은 날짜 내 순번을 사용합니다. 아래 항목은 작업 규모에 맞춰 간결하게 작성합니다.

```markdown
## YYYY-MM-DD · 순번 · 작업명

- 요청/범위:
- 변경 내용 및 관련 파일/문서:
- 주요 결정과 근거:
- 검증: 실행한 명령, 결과, 검증 범위
- 남은 사항/제약: 없으면 없음. 미수행은 명시
```

완료된 구현과 제안·초안·계획을 구분합니다. 실제 외부 연결이나 배포 없이 코드만 준비한 경우 연결·배포 완료로 표기하지 않습니다. 이전 작업의 테스트 결과를 이번 작업에서 다시 실행한 것처럼 기록하지 않습니다.

## 코드 작성 형식

사용자가 코드를 계속 확인할 수 있도록 줄바꿈과 들여쓰기를 유지합니다. 자동 포맷을 적용한 뒤에도 변경 내용을 직접 읽고 중첩 구조와 처리 흐름을 확인합니다.

- 들여쓰기는 공백 2칸, 줄바꿈은 LF, 파일 끝에는 개행을 사용합니다.
- 한 줄 길이는 100자를 기준으로 Prettier가 조정합니다. URL·문자열 등 분리하면 의미가 달라지는 값은 예외입니다.
- JSX 중첩 요소는 구조가 드러나게 줄을 나누고, 속성이 여러 개인 태그는 속성마다 줄을 나눕니다.
- CSS는 선언마다 줄을 나누고, 규칙 사이에는 빈 줄을 둡니다. 미디어 쿼리 내부도 같은 기준을 적용합니다.
- 여러 실행문을 한 줄에 넣지 않습니다. 복잡한 조건·콜백·객체는 여러 줄로 펼치고, 초기화·이벤트 처리·렌더링 등 논리 단위 사이에는 빈 줄을 둡니다.
- TypeScript/JavaScript는 작은따옴표, 세미콜론 생략, 여러 줄 항목의 후행 쉼표를 사용합니다. JSX 속성은 큰따옴표를 사용합니다.

`.prettierrc.json`에 포맷 기준을, `.editorconfig`에 편집기의 기본 들여쓰기·개행 기준을 둡니다. `.prettierignore`에서 빌드 결과·의존성·잠금 파일·기존 템플릿 자산을 제외합니다.

```sh
pnpm format
pnpm format:check
```

첫 명령은 파일을 정리하고, 두 번째 명령은 파일을 수정하지 않고 형식 준수 여부를 확인합니다. 포맷 검사는 린트·타입 검사·테스트와 함께 사용합니다.

## Git Flow 적용

브랜치 이름·커밋·PR·릴리스 및 충돌 처리의 상세 기준은 [팀 개발 규칙](TEAM_RULES.md)을 확인합니다. 문서·테스트·설정 작업에도 이슈와 작업 브랜치 절차를 적용합니다.

1. 작업 목적·완료 조건·담당자·우선순위·관련 영역·의존성을 담은 이슈를 생성하거나 확인합니다. 별도 문제는 새 이슈로 분리합니다.
2. `git status`와 diff로 현재 변경을 먼저 확인합니다. 미커밋 변경은 목적을 파악하여 해당 이슈·작업 브랜치에서 관리하며, 임의로 버리거나 무조건 stash하지 않습니다. `main`·`develop`에 직접 커밋하지 않습니다.
3. 깨끗한 작업 트리에서 `develop`을 최신화한 뒤 목적에 맞는 작업 브랜치를 만듭니다. 브랜치 유형과 예외적인 릴리스·핫픽스 기준은 팀 규칙을 따릅니다. 이슈 번호는 실제 등록된 번호를 사용합니다.
4. 논리 단위로 Conventional Commits를 작성합니다. 변경 코드·staged diff를 직접 확인하고, 필요한 테스트·포맷 검사·린트·빌드와 문서 갱신을 수행합니다.
5. PR 전 `develop` 최신 변경을 반영합니다. 단독 브랜치는 rebase하고 공동 브랜치는 합의한 방식으로 동기화합니다. 일반 작업 PR의 대상은 `develop`입니다. PR 본문에는 작업 내용, 변경 이유, 확인 방법, 영향 범위, 체크리스트와 관련 이슈를 포함합니다. 미수행 검증은 이유와 수동 확인 방법을 적습니다.
6. 최소 1명의 승인과 필요한 관련 담당자 승인을 받은 뒤 팀의 병합 방식으로 반영합니다. 기능·수정은 squash merge, 릴리스·핫픽스는 merge commit을 사용합니다. 릴리스·핫픽스는 `main`·`develop` 양쪽 반영과 버전 태그를 확인합니다.
7. 병합 후 이슈와 작업 브랜치를 정리합니다. 로컬 문서 반영·구현·검증과 팀의 완료 기준 충족 여부를 구분하여 [작업 이력](WORKLOG.md)에 기록합니다.

### 저장소 준비가 필요한 경우

- 원격에 `develop`이 없으면 저장소 관리자와 팀의 최초 설정 절차에 따라 준비합니다. 이미 `main`이 있는 저장소에서는 팀 규칙의 `master` 이름 변경 예제를 반복하지 않습니다.
- 원격 `main`·`develop`의 보호 설정으로 직접 푸시·강제 푸시를 제한합니다. 문서에 규칙을 적는 것과 원격 보호 설정을 적용하는 것은 별개이며, 실제 적용 여부를 확인한 뒤 기록합니다.
- 기존 미커밋 작업은 보존하면서 목적별 이슈·작업 브랜치 연결을 먼저 정리합니다. `develop` 부재를 이유로 `main`에 바로 커밋하거나 최신 `develop`에서 분기한 것처럼 기록하지 않습니다.

현재 브랜치 구성과 준비 상태의 확인 시점은 [문서 색인](README.md)과 [작업 이력](WORKLOG.md)을 참고합니다.

## Git 추적 및 제외 기준

`.gitignore`는 로컬 설정·비밀값과 재생성 가능한 산출물을 제외하고, 실행·검토·협업에 필요한 파일은 유지합니다.

| 구분               | 제외 대상                                                                  | Git에 유지할 대상                                     |
| ------------------ | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| 의존성             | `node_modules`, `.pnpm-store`                                              | `package.json`, `pnpm-lock.yaml`                      |
| 빌드·테스트·캐시   | `dist`, `dist-ssr`, `coverage/`, `.nyc_output/`, `.vite/`, `*.tsbuildinfo` | 소스, 테스트 코드, Vite·Vitest·TypeScript 설정        |
| 환경변수·로컬 설정 | `.env`, `.env.*`, `*.local`                                                | 비밀값 없는 `.env.example`                            |
| 로그·편집기        | 로그, OS 메타데이터, 로컬 편집기 설정·임시 파일                            | 기존 허용 대상인 `.vscode/extensions.json`            |
| 작업·개발 기준     | 해당 없음                                                                  | `docs/`, `AGENTS.md`, 린트·포맷 설정, `.editorconfig` |

`.env.example`의 예외 규칙은 `.env.*` 뒤에 둡니다. 샘플 파일에는 실제 키·토큰을 넣지 않습니다. `.prettierignore`는 포맷 대상만 제어하므로 Git 추적 여부와 별도로 관리합니다.

규칙을 변경하면 `git check-ignore --no-index`로 실제 파일과 가상 경로를 확인합니다. 제외할 경로뿐 아니라 `.env.example`, 잠금 파일, 소스·문서·설정 파일이 제외되지 않는지도 확인합니다.

```sh
git check-ignore --no-index -v .env .env.production .env.local coverage/lcov.info
git ls-files -ci --exclude-standard
git diff --check
```

`.gitignore`는 이미 추적 중인 파일을 자동으로 추적 해제하지 않습니다. 두 번째 명령으로 현재 인덱스의 제외 대상을 확인하며, 출력이 있으면 파일별 용도와 추적 상태를 검토합니다. 이 점검은 현재 작업 트리·인덱스를 대상으로 하며 과거 커밋 내용까지 검사하지 않습니다.

## 검증 기준

- 코드 변경은 포맷 검사를 수행하고 관련 테스트·린트·빌드를 확인합니다. 새 변경이나 실패가 없다면 동일 검증을 불필요하게 반복하지 않습니다.
- UI 변경은 가능하면 실제 브라우저에서 확인합니다. 시각 검증이 불가능하면 제한 사항을 기록합니다.
- 문서만 변경한 경우 링크 대상, 파일·명령·환경변수와 구현의 일치 여부, `git diff --check`를 확인합니다. 이를 위해 앱 테스트를 새로 만들거나 전체 테스트를 재실행할 필요는 없습니다.
- 실환경 키·서버·도메인이 없어 확인하지 못한 항목은 해당 조건과 함께 미검증으로 기록합니다.

## 작성 기준

- 기본 작성 언어는 한국어입니다. 명령, API 필드, 코드 식별자는 원문을 유지합니다.
- 문서 간 링크는 저장소 기준 상대 경로를 사용해 다른 환경에서도 열리도록 합니다.
- 실제 API 키, 토큰, 비밀번호 등 비밀값은 문서에 넣지 않습니다. 환경변수 이름과 대체값을 사용합니다.
- 오래된 링크와 상태는 갱신하되, 관련 없는 기존 작업과 사용자 변경을 덮어쓰지 않습니다.
